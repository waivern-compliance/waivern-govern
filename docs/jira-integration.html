Jira, and what may be delegated to it

Governance work that belongs in a sprint should reach the sprint. The question worth settling first is which work that is, because the difference decides the design.

Prepared for the BBC Privacy and AI Governance Platform RFI Extends the P3 integration rows of the requirement map

Why this is worth doing at all

A privacy task assigned to an engineering lead lands in a system they do not open. It is not ignored out of indifference; it is invisible.

That is the actual failure mode this addresses. The platform can raise a mitigation, name an owner, set a service level and record a breach when it lapses — and none of that helps if the person who has to do the work lives in a Jira board and hears nothing.

The requirement map lists Jira at P3 as “mitigation actions as issues, status returned”. That scoping is narrower than “sync tasks with Jira”, and deliberately so. The rest of this annexe explains why the narrow version is the correct one rather than a reduced one.

The rule: Jira may carry the work, not the attestation

The platform holds seven kinds of task. They are not equally delegable, and treating them as though they were is the way this integration goes wrong.

  1. ✓ Mitigation due — fully delegable Engineering work that belongs in a sprint. When somebody closes the issue, the work genuinely happened, and that closure is legitimate evidence for closing the task here. This is the one case where state flows back into the platform. Issue closed in Jira → task completed in Govern
  2. ~ Answer a section · reassess · verify a mitigation A ticket can carry the prompt and the deadline. It cannot carry the act: the answers are the record, and verification is a person other than the owner confirming a control is in place. The ticket points at the platform and closes when the work is done here. Issue created as a pointer · closed by Govern, never the reverse
  3. ✕ Approve a stage · review an acceptance · privacy review Role-gated attestations. Approving an assessment and accepting a risk sit with the approver alone, separated on purpose from the ability to edit the record. A configuration in which closing a Jira issue approves a DPIA would undo the audit chain's entire claim, and no amount of convenience is worth that. No issue raised, or a read-only reference at most
The test

If completing the work is itself the governance act — an approval, an acceptance, an answer that becomes part of the record — it stays here. If the governance act is recording that the work was done, the work can live wherever the person doing it lives.

How a mitigation travels

The delegable case, end to end. Only the step in colour changes state in the platform, and it is triggered by evidence rather than by assertion.

Raised A mitigation is recorded against a risk, with an owner and a date
Pushed An issue is created in that team's project, holding the key
Worked The team does it where they already work
Reconciled The sweep reads the issue status and completes the task

The issue key is stored on the task, so a sweep that runs a thousand times creates one issue. Everything already in the platform behaves this way — tasks, notifications and outbound deliveries all carry idempotency keys — and an integration that did not would produce a board nobody could use within a day.

Build the seam, not the integration

The requirement map lists ServiceNow directly above Jira, described as “outbound task creation and status sync”. That is the same shape with a different vocabulary: create an item of work somewhere else, hold its identifier, read back whether it is finished.

So the thing worth building is a work tracker seam with one adapter per system, rather than a Jira feature. Jira and ServiceNow then differ by configuration and a small client, not by a second design. Microsoft Lists, also at P3, reads through the same shape.

That seam's shape is already in the platform: one connection kind for work trackers, a configuration holding the destination and the statuses that mean finished, and the two identifier fields on a task. Neither adapter is written; neither needs a migration before it can be.

  • Which project, and whose. One privacy project is simplest and least useful; raising into each product team's own board is what makes the work visible to the people who must do it. Mapped per entity.
  • Which statuses mean done. Jira workflows are per-project and every organisation customises them, so this is configuration rather than code. A status mapping nobody can edit is an integration that breaks the first time a team adds a column.
  • Field mapping. Issue type, and whether the due date and service level are pushed as fields or written into the description.

Poll rather than receive

Jira can push webhooks when an issue changes. The recommendation is to poll from the scheduled sweep instead, and it is not a shortcut.

  • No inbound endpoint. A platform whose argument is the integrity of its audit chain should add attack surface only where it buys something. Sub-minute latency on a mitigation due in three weeks buys nothing.
  • It works behind a boundary. If the instance is Data Center inside the network, an outbound poll works and an inbound webhook needs an exception.
  • It is already idempotent. The sweep runs hourly and re-running it converges on the same state. Reconciliation is exactly the kind of work it was built for.

A webhook receiver can be added later for the organisation that wants it, without changing what reconciliation does.

What it costs

Estimates assume the existing codebase, which already provides per-organisation encrypted credentials, scoped connection kinds, outbound delivery with backoff, and an hourly reconciliation job.

Already in place

The three decisions that would otherwise make the second adapter expensive have been taken, so the figures below are not resting on work still to be argued about. A task carries a machine identifier and a human reference separately, because Jira and ServiceNow disagree about whether those are the same thing. A destination is a map in the connection's configuration rather than named columns, so ServiceNow's table and assignment group need no schema change. And completion is matched against stored strings, so a ServiceNow state of 3 and a Jira status of “Done” go through one comparison.

What remains for each product is a client, a form, and the reconciliation step — which is what the figures describe.

ScopeContentsEffort
One way Connection and credentials, Jira client, an issue raised per mitigation holding its key, closing here closes there. Configuration screen for project and issue type. 1.5–2 days
Both ways The above, plus status mapping and reconciliation in the sweep, so a closed issue completes the mitigation task. 4–4.5 days
ServiceNow after it A second adapter against the same seam. No new design. 1–1.5 days
Issues that start assessments A new issue in nominated projects raises a screening — privacy reached at the point work is proposed rather than after it ships. +2 days

The last row is the one with the most governance value and the least certainty. It depends on the BBC having project conventions consistent enough to decide which issues warrant screening, which is a question about the organisation rather than about software.

What would change these numbers

Cloud or Data Center

Jira Cloud with an API token is trivial to authenticate. OAuth 2.0 3LO adds roughly a day and a consent flow. Data Center uses personal access tokens and may sit behind a network boundary, which settles the polling question rather than leaving it as a preference.

One board or many

Raising every issue into a single privacy project is a day cheaper and substantially less useful. Per-team projects need an entity-to-project mapping and someone at the BBC who can say what that mapping is.

Who reconciles a disagreement

A task completed here while its issue stays open, or the reverse. Govern holds the governance state and Jira closure is evidence feeding it, never the other way round — but somebody has to decide whether a reopened Jira issue should reopen a completed mitigation. It is a policy question, and it should be answered before launch rather than discovered.
